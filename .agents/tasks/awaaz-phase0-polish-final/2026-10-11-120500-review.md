# Multi-item complaint capture + multi-card verdict rendering

The change makes a single submission that names several commodities produce one fully-formed `Complaint` row per item, grouped under a shared `submission_id`, and renders one verdict card per row on the frontend. The backend adds an additive indexed `submission_id` column (idempotent startup migration), a collect-all rates resolver (`find_all_items`), a multi-item AI pipeline (`parse_complaint_items`) that never raises and keeps `parse_complaint_text` byte-compatible, a `MultiComplaintResponse` returned by both POST handlers persisting N rows in one transaction, and the frontend renders the cards under an "N violations detected" header with the transcript and map shown once. The committed implementation matches the approved design and the acceptance criteria; the full backend suite (47 tests) passes and the frontend lints and builds clean.

Watch for: an **uncommitted** CORS behavior change in `awaaz_backend/main.py` that contradicts the task's "auth/CORS/admin untouched" constraint (confirmed); the committed Whisper engine swap (OpenAI `whisper` → `faster-whisper`) bundled into the multi-item commit (confirmed); and verification-time leftovers — empty scratch DB files and a stray `DATABASE_URL` env override — that are not cleaned up (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The persistence, schema, pipeline, router, and frontend layers all land exactly as the design specifies, and I verified the behavior rather than trusting the FEAT reports: the aaloo+pyaaz driver yields two rows — Potato (reported 150 / official 100 / +50.0%) and Onion (reported 200 / official 120 / diff 80.0 / +66.7% / High) — sharing one `submission_id`, with `primary.item_canonical_id == "pyaaz"` and the Onion sorting to index 0. The migration is additive and idempotent across fresh/migrated/restart, and `parse_complaint_text` is preserved as a `parse_complaint_items(...)[0]` facade so every pre-existing single-item test still passes.

The one hard constraint that is violated is NFR6's "no CORS change": `main.py` carries an uncommitted working-tree edit that flips `allow_credentials` and rewrites the origin handling. Because it is uncommitted it is not in any task commit, but it sits in the worktree and would ship if the tree is merged as-is; it needs to be reverted or explicitly carved out into its own change.

The Whisper engine was swapped from OpenAI `whisper` to `faster-whisper` inside the FEAT-001 commit. This is outside the multi-item scope, but it is why the backend is importable at all on this machine — the stock `whisper` path pulls in `tiktoken`, whose native DLL is blocked by an Application Control policy here, so `main` cannot even collect its API tests. The swap keeps the import lazy (NFR5 holds). It is a justified but genuinely unrelated change bundled into the feature commit, and the reviewer/author should decide whether it belongs in this task.

The verification environment left artifacts behind: a `DATABASE_URL=...\_scratch_verify.db` process env override and empty `_scratch_verify.db` / `awaaz_scratch_feat001.db` files. With that stray env var set, `pytest -q` fails 9 API tests ("no such table"); once it is cleared the suite is 47/47 green. The code is correct — the failures were purely the leftover override pointing the engine at an empty DB — but the design explicitly asked to clean up scratch files, and leaving a `DATABASE_URL` override in the working shell is a trap for the next run.

### submission_id column and idempotent migration

`db/models.py` adds `submission_id = Column(String(36), nullable=True, index=True)` right after `id` and surfaces it in `to_dict()`; `db/session.py` runs a `PRAGMA table_info("complaints")`-guarded `ALTER TABLE ... ADD COLUMN` + `CREATE INDEX IF NOT EXISTS` inside the same `engine.begin()` block as `create_all`, only on SQLite. I confirmed the live `awaaz.db` already carries `submission_id` appended at the end of the column list (the migrated-in-place path), while a fresh DB gets it from `create_all` — and `init_db()` run twice in a row succeeds, so the guard is genuinely idempotent across fresh/migrated/restart (AC11, confirmed).

### find_all_items collect-all resolver

`services/rates.py` gains `find_all_items`, which scans `_alias_map` under the lock and collects **every distinct** canonical id whose alias (len ≥ 3) matches by exact/substring, de-duped by canonical id in insertion order. It deliberately omits `resolve_item`'s greedy RapidFuzz tier-4 and its single-return, which is what lets discovery find both commodities instead of dropping the second. `find_all_items("aaloo aur pyaaz dono mehnge")` returns `{aloo, pyaaz}` (confirmed). `resolve_item`/`compare_price` are untouched.

### Multi-item pipeline, never-raises, byte-compatible facade

`parse_complaint_items` wraps its whole body in a try/except that logs and returns a one-element "Unspecified" fallback, so it never raises and always yields ≥1 item (confirmed). It computes `det_lang`/`rule_cat`/`rule_urg` once, segments clauses, builds an LLM list (via `_call_ollama_llm_multi` with the `{"items":[...]}` wrapper schema and per-item clause attribution) and a rule list (`_discover_items_by_rules` over `find_all_items`), then unions and de-dupes by canonical id with the **rule price authoritative when > 0** and the LLM's category/urgency/native text layered on. Results sort by `percentage_overcharge` desc. `parse_complaint_text` is re-expressed as `parse_complaint_items(text)[0]`, and every pre-existing `test_pipeline.py` assertion still passes, so single-item output is unchanged.

One deviation from the literal design is documented and sound: because the ` bhi ` connective splits "Pyaaz" from "200 rupay kilo" into separate clauses, `_price_clause_for` borrows the next price-only clause (that names no other commodity) when a single-commodity clause has no price. This is what attributes 200 → pyaaz while keeping the connective split. The merge logic layers LLM category/urgency onto a rule row without recomputing the comparison when only the price source changes, but since the derived comparison fields travel together with the chosen `reported_price`, the merged row stays internally consistent — I traced the four price-derived keys being copied as a group.

### MultiComplaintResponse and single-transaction persistence

`schemas.py` adds `submission_id: Optional[str]` to `ComplaintResponse` (between `id` and `created_at`) and a `MultiComplaintResponse { submission_id, complaints, primary }`. `routers/complaints.py` factors both POST handlers into `_persist_submission`, which calls `parse_complaint_items` in a threadpool, generates one `submission_id`, builds one `Complaint` per item with `**shared` metadata, does a single `add_all` + one `commit` (all-or-nothing, NFR4), refreshes, overcharge-sorts, and picks `primary` via an explicit `_select_primary` (max overcharge, tie-break urgency rank High=3/Medium=2/Low=1). The voice handler keeps its full temp-dir/FFmpeg/Whisper/400/503/`finally rmtree` path and additionally offloads the blocking save/convert/transcribe steps to the threadpool — an in-scope robustness improvement that does not change the response contract. GET/PATCH/list are unchanged except they now carry `submission_id`.

### Backend tests green including the driver

`pytest -q` is **47 passed** once the stray `DATABASE_URL` override is cleared. The API test `test_multi_item_complaint_splits_into_two_rows` asserts the full contract: `len(complaints)==2`, shared `submission_id`, two distinct ids, Potato (150/100/+50.0, PERA), Onion (200/120/diff 80.0/+66.7/High), `primary.item_canonical_id=="pyaaz"`, identical `transcript_raw`/`location_area` across rows, and `submission_id` on the PATCH response. The pipeline tests pin the same per-item numbers, prove `find_all_items` returns both ids, prove one-commodity-per-clause segmentation, prove the rule price overrides a conflicting LLM price (999 → 150), and prove `_select_primary` returns the pyaaz row. These are specific value assertions, not smoke checks.

With the leftover `DATABASE_URL=...\_scratch_verify.db` env var still set, 9 API tests fail with "no such table: complaints" because the engine opens an empty scratch DB and the lifespan `init_db()` does not fire under a module-level `TestClient`. This is an environment artifact of the verification run, not a code fault — clearing the override restores 47/47.

### Frontend multi-card render

`lib/api.js` adds `normalizeComplaintResult` returning `{ submissionId, complaints, primary }` for both the new shape and a legacy single object. `ReportSection.jsx` lifts the verdict block into an inner `VerdictCard` rendered per complaint: rose/emerald theming and the three Badge variants keyed off `percentage_overcharge > 0` / `item_name`, `formatPrice`/`formatVariance`, the `font-urdu` RTL branch for `detected_language === 'Urdu'`, the per-card Replay-Voice `speakText`, the per-card `needs_review` notice, and per-card Copy-ID driven by `copiedId === complaint.id`. The dead `|| is_violation` term is dropped. The count header uses `t.verdict.violationsCount.replaceAll('{count}', ...)` only when `complaints.length > 1`; the shared transcript renders once from `primary.transcript_raw` and `MiniLocationMap` once from `primary` guarded by `primary?.lat && primary?.lng`; the avatar reaction maps complaints to chips capped at 6 and speaks only `primary.native_response`. `npm run lint` is 0/0 and `npm run build` succeeds (the >1000 kB chunk notice is pre-existing vendor-three). The new `violationsCount` key is present in **both** the `en` and `ur` verdict blocks.

### Auth / admin / no push

`auth.py` is unchanged versus `main`. The admin API-key dependency is untouched. The three task commits are local to `polish/final` with no upstream tracking branch — nothing is pushed.
