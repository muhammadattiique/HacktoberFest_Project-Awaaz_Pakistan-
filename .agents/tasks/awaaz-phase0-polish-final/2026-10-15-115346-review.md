# Per-item price attribution and regional-script resolution for chained complaints

Two bugs in the Awaaz Pakistan complaint parser are fixed on `polish/final`. BUG 1: when a complaint chains several item/price pairs ("tomatoes at 250 ... and sugar at 180 ..."), the later commodities stole the first clause's price because the clause never split on the native connectives and a multi-commodity clause only ever read the first plausible number. BUG 2: Pashto/Sindhi item names and Pashto/Punjabi number words were not recognized, so staples never resolved and `تن سو پنجاہ`=350 failed to parse. The fix adds three native connectives to clause segmentation, a positional nearest-price attribution helper for multi-commodity clauses, a conservative Arabic→Urdu script-variant fold, new aliases, and the missing number words — all additively, without widening the word-boundary matching discipline that keeps the 7-item test free of a phantom Chicken. Scope is backend-only; `complaints.py`, auth/CORS/schema, and the lazy whisper imports are untouched.

Watch for: nothing blocking. The Sindhi/Pashto native spellings are explicitly best-effort and carry `NATIVE-REVIEW-REQUIRED` markers (confirmed); the rate-list spellings can't carry inline comments so they live in the FEAT findings as the constraint required.

**Verdict**: APPROVED

## High-level view

The segmentation fix is the primary lever: `_segment_clauses` now splits on ` او ` (Pashto), ` تے ` (Punjabi Shahmukhi), and ` ۽ ` (Sindhi) in addition to every pre-existing delimiter, so each item/price pair lands in its own clause and the single-commodity own-clause/borrow-next (` bhi `) path handles it unchanged. For the residual case where one clause still names 2+ commodities, a new positional helper assigns each commodity the nearest price token that follows it (nearest preceding as fallback) and hands `_reconcile_item` a per-commodity sub-clause instead of the whole clause — so a trailing commodity can no longer read the leader's number. The helper locates commodities with the exact `(?<!\w)alias(?!\w)` pattern `find_all_items` uses, so it never widens matching.

Resolution of regional names is handled by a conservative script fold in `rates.py` that maps only Arabic yeh/alef-maksura/kaf to their Urdu forms, applied symmetrically to both the alias-map keys and the query text, so Pashto پياز (Arabic yeh) matches rate-list پیاز (Urdu yeh). Heh variants are deliberately left unfolded to avoid collisions. New aliases cover the Pashto/Sindhi staples and the Punjabi/Pashto tea spellings reuse the existing `chai_patti` item at its unchanged SAMPLE price — no new tea item.

Number parsing gains the full Pashto numeral set plus Punjabi تن=3 / پنجاہ=50 in `BASIC_NUMBER_WORDS`, and `parse_word_numbers` gains the matching compound-hundred/thousand prefixes with ordering care (سوه before سو, زره before زر) so `دوه سوه`=200 is not half-matched. The under-rate registration filter in `complaints.py` is untouched, so items selling at or below the official rate still stay out of registration.

### Segmentation on native connectives

`_segment_clauses` appends ` او `, ` تے `, ` ۽ ` to the existing `re.split` alternation. The tokens are space-padded, so ` او ` cannot overlap the already-present ` اور ` (confirmed: the probe `ٹماٹر 250 روپۍ کيلو او چینی 180 روپۍ کيلو` returns two separate clauses). This is the primary fix — once the pair is split, each clause has one commodity and the untouched single-item path attributes correctly.

### Positional attribution for multi-commodity clauses

`_attribute_prices_positionally` is the secondary hardening for clauses that still resolve to 2+ commodities. It measures both commodity positions and price-token positions on the same `parse_word_numbers(normalize_digits(clause))` string, so they are comparable; price tokens use the same `10<=n<=10000` plausible-PKR rule (excluding 2024-2026) as `extract_price_and_normalize`. Each commodity takes the nearest unused price token that follows it, falling back to the nearest preceding unused token, and each token is consumed once — so two commodities with two prices can't both grab the same number.

```
clause:   tamatar 250 ... chini 180
positions: ^C1    ^P1      ^C2   ^P2
C1 -> first following unused price -> P1 (250)
C2 -> first following unused price -> P2 (180)   # P1 already consumed
```

A commodity with no attributable price falls back to the whole clause and `price=None`, so behavior never regresses below the old whole-clause read. The alias search uses the identical `(?<!\w)alias(?!\w)` pattern and the same `len>=3` cutoff as `find_all_items`, so positional attribution introduces no new fabrication risk — the phantom-Chicken probe still returns empty and the exactly-7 test still passes.

### Script-variant fold for regional names

`_normalize_script` folds only Arabic yeh (U+064A→U+06CC), alef-maksura (U+0649→U+06CC), and Arabic kaf (U+0643→U+06A9). It is applied when building every alias-map key in `load()` and to the query text in both `resolve_item` and `find_all_items`, so the folding is symmetric and a Pashto پياز matches the rate-list پیاز despite the code-point difference. The word-boundary regex is unchanged, so this is additive normalization, not substring widening. Heh variants are intentionally not folded, with a greppable marker explaining the collision risk.

### Number words and compound parsing

The Pashto numerals (يو…زره) and the two missing Punjabi words (تن=3, پنجاہ=50) land in `BASIC_NUMBER_WORDS`. In `parse_word_numbers`, the compound-hundred list adds سوه before سو and the thousand list adds زره before زر, so `دوه سوه`=200 is not half-consumed by a shorter `سو`/`زر` match — the ordering is the correctness detail here. Probes confirm `يو سل پنځوس`=150, `دوه سوه`=200, `تن سو پنجاہ`=350.
